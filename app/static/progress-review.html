Getting to a Simple On-Premise Deployment

4 done

The gap between "a working app" and "something district or church IT can actually stand up" is usually the hard part. That gap is closed.

One-command startupDone

The entire app — database included — starts with a single docker compose up. No manual server setup, no separately-installed database, no pip-install-and-hope.

Automatic database migrationsDone

Schema changes apply themselves on container start. No one has to hand-run SQL to install or upgrade this.

Starter data & onboarding scriptsDone

A bootstrap script creates the first admin account; a demo-seed script can populate a realistic sample org for training or a sales walkthrough.

Works from a phone on the same networkDone

The web UI is mobile-responsive — a hamburger menu on small screens and horizontally-scrollable tables — so a principal or pastor checking Rocks from a phone isn't stuck squinting at a desktop layout.

Proven, not just claimedDone

This isn't "the build succeeded" — it has been deployed end-to-end to a real server and walked through as a live app in a browser: login, adding a Rock, updating the scorecard, the works. The exact same container images are what would run inside a district's or church's own server room.

Security Posture

7 active · 3 near-ready

What's already protecting the app today, and what's a deployment step — not a redesign — away from being finished.

Passwords are hashed, never stored in plain textActive

Local sign-in uses bcrypt password hashing throughout.

Role-based access controlActive

Admin / member / viewer roles are enforced on every route, not just hidden in the UI.

CSRF protectionActive

Every state-changing request is checked against a double-submit CSRF token.

Login rate limitingActive

Repeated failed logins from the same source are throttled to blunt password-guessing attempts.

Locked-down session cookiesActive

Session cookies are HttpOnly (invisible to page scripts) and restricted with SameSite, so they aren't a soft target for the usual cookie-theft tricks.

Security response headersActive

Clickjacking protection, MIME-type sniffing protection, and controlled referrer leakage are set on every response.

Zero telemetryActive

No analytics beacons, no usage tracking, no outbound calls reporting anything about how the app is used. Nothing about a district's or church's data leaves their server, by design.

HTTPS (TLS) + Secure cookie flagNear-ready

The code already supports this behind a single configuration flag — it's off only because the current public demo server doesn't have a certificate. Turning it on for a real deployment is a standard reverse-proxy-plus-certificate step, not new development.

Needs a domain name pointed at wherever the app is hosted, or an internal certificate if it's staying entirely inside a private network.
Deployment-specific secretsNear-ready

The database password and app secret key ship with safe-for-testing defaults today. Generating real, org-specific values is a documented checklist step at install time, not a code change.

Content-Security-Policy headerNear-ready

A small amount of inline-script cleanup away from a tighter CSP header — scoped and understood, just not done yet.

On-Premise, Not Cloud

This is not a hosted product districts or churches sign up for. It's software they run.

There is no multi-tenant cloud service behind this app, and none is planned. From the first line of the project's own build rules: no required external or cloud dependencies — no calls to hosted SaaS APIs, no cloud database, no third-party identity provider as a condition of the app working.

It runs entirely inside Docker containers on hardware the district or church owns or leases, sitting inside their own network, behind their own firewall — the same posture as any other internal administrative system they already run.

  • No internet dependency at runtime. Once installed, nothing about normal day-to-day use requires an outside connection — no license phone-home, no CDN-loaded scripts or fonts, no third-party service the app quietly depends on to function.
  • Air-gap friendly. A network that's heavily firewalled, or fully disconnected from the internet, is a supported target, not an edge case.
  • Staff still just use a browser. Nothing changes about how people access it day to day — the difference is what's on the other end of that connection: the organization's own server, not a third party's.
  • The public demo is a convenience, not a preview of a hosted product. It exists only so this can be reviewed and clicked through before anyone commits infrastructure. The container images running there are identical to the ones that would run in a server closet.
Bottom line: the app itself is done — all nine tools, hardened, containerized, and proven end-to-end on a live server. What separates today's demo from a real district or church deployment isn't more building, it's a short, well-understood checklist (TLS, secrets, a couple of decisions about calendar/email/SSO) — all covered in the companion What's Left & Feasibility Review.
