Authorization & Access Control

6 open

Mostly engineering work with no district/church decision attached — the exceptions are called out.

Team-scoped data accessMediumInput needed

Members and viewers can currently read and write any team's Rocks, Issues, Scorecard, etc., not just their own. Mechanical to fix — row-level scoping on existing queries — but touches every route.

Ask districts/churches: do they want strict team isolation, or is org-wide visibility actually preferred for a small staff (common for a single-campus church)?
Refresh tokens & session revocationMedium

Access tokens are 24-hour bearer JWTs with no server-side kill switch — offboarding a staff member today doesn't invalidate their active session. Standard fix, no open decision.

Password reset flowLow–Medium

Straightforward once outbound email exists (see the Email item under Integration below) — this is blocked on that, not on difficulty.

Audit logLow–MediumInput needed

Log role changes and deletes. Simple once scoped.

Ask: how long should logs be retained? A district's records-retention policy and a church's may differ, and neither has been specified yet.
Content-Security-Policy headerLow

A few inline scripts need to move to external files first; then a real CSP can be turned on. Pure cleanup, no decision.

Rate limiting: per-account + distributed-safeLow

Current limiter is per-IP and in-memory — fine for one instance, blind to a distributed attack or a multi-worker deployment. Only matters if this ever runs on more than one app instance.

Ops & Deployment Readiness

4 open

This is the category to read carefully — two of these are genuinely required before real district or church data goes anywhere near this app.

TLS + secure cookiesLow–MediumInput needed

Blocking for real use. The app currently serves plain HTTP; login cookies aren't marked Secure to match. Fine for a private demo, not acceptable once real staff credentials or student-adjacent data are involved. Fix is a reverse proxy (nginx/Caddy) with a certificate — well-understood, not a big lift.

Ask: will the hosting org (district IT, or whoever hosts it for a church) provide a domain name they can point at the server for a real certificate, or does this run entirely inside a private network on a self-signed/internal cert instead?
Production-safe secretsLow

Blocking for real use. The database password and app secret key currently ship with safe-for-testing defaults. Each real deployment needs its own generated values — a deployment checklist item, not a coding task.

Automated test suiteMedium–High

Everything so far has been verified by hand — manual API calls and live browser clicks. Not a blocker for continued demo use, but a real risk once this holds live data and changes keep landing. Ongoing effort, not a one-time task.

CI pipelineLow

Cheap once a test suite exists to run — not worth building ahead of it.

Microsoft & Google Integration

0 of 3 started

"Integration" is really three separate features with very different effort levels. Worth not lumping them together when scoping — email is a near-term win; calendar sync is a real project.

Sign-in with Microsoft / Google (SSO)MediumInput needed

Lets staff log in with the Microsoft 365 / Google Workspace account they already use, instead of a separate app password. The data model already anticipates this (a provider field on the user record sits unused). Well-documented OAuth2/OIDC pattern — the effort is real but not exotic.

  • Which platform(s)? Districts likely run Microsoft 365 or Google Workspace org-wide; many churches don't have a managed tenant at all and rely on personal Gmail accounts — that changes what's even possible here.
  • Who approves the OAuth app? District IT security review, or whoever administers the church's Workspace/365 subscription, needs to register the app and grant consent. This is often the slowest step, not the code.
  • Auto-create accounts on first login, or require pre-provisioning by an admin?
  • Keep local password login as a fallback, or replace it once SSO works? (CLAUDE.md's on-prem rule means local login stays available regardless — this is about default behavior, not a hard requirement to drop it.)
Calendar sync (Outlook / Google Calendar)Medium–HighInput needed

The biggest single piece of remaining work. Requires the Meeting datetime change above, an OAuth consent flow per user or resource calendar, secure storage of refresh tokens, and — if two-way sync is wanted — webhook subscriptions that expire and must be renewed, plus logic for what happens when the app and the calendar disagree.

  • One-way or two-way? "Meeting shows up on my calendar automatically" (push-only) is meaningfully simpler than keeping changes in sync both directions.
  • Personal calendars per staff member, or one shared team calendar?
  • Which platform(s) — same tenant/consent question as SSO above, and the two features can share the OAuth plumbing if both are wanted.
Email notificationsLowInput needed

The app currently sends no email at all, by any method — this is the actual gap, not "Microsoft/Google" specifically. Plain SMTP (works against a district or church's existing mail server, or a Microsoft 365 / Google Workspace account with an app password) unlocks password reset, meeting reminders, and scorecard-due nudges, with no OAuth required. This is the cheapest, highest-leverage item on this whole page.

  • Whose mail server? Their own relay, or an app password on an existing Microsoft/Google account.
  • Which events should actually send email — just password reset, or also reminders and weekly digests? Over-notifying is a fast way to get an EOS tool ignored.

Recommended Sequencing

Ordered by technical dependency and risk, not necessarily by what matters most to the business — reorder freely.

  1. Email / SMTP notifications — low effort, no OAuth, unlocks password reset immediately.
  2. Password reset flow — depends directly on #1.
  3. TLS + secure cookies, production secrets — required before any real staff data touches this, regardless of what else ships.
  4. Meeting date/time + agenda model — hard prerequisite for calendar sync later.
  5. Automated tests — de-risks everything above before real orgs depend on it.
  6. Sign-in with Microsoft / Google — the single biggest quality-of-life win for real deployments, but needs district/church IT coordination started early since approval is often the slow part.
  7. Calendar sync — builds on #4 and reuses #6's OAuth plumbing; the largest remaining project.
Bottom line: nothing left is architecturally risky — every item above fits the on-prem, no-required-external-dependency approach this app was built around from the start (SSO, calendar, and email are all additive, not load-bearing). The fastest path to a trustworthy pilot with a real district or church is items 1–5: cheap, no external decisions blocking them, and they close the gap between "demo" and "safe to hold real data." Items 6–7 are worth starting the IT-approval conversation on now, even before the code, since that approval step is usually slower than the engineering.
